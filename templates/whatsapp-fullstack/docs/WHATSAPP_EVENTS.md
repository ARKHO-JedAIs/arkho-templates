# WhatsApp events map

What WhatsApp can deliver to this template, what the code does with each event
today, and what we recommend doing with it. For developers extending
`backend/src/lambda/whatsapp/ws-handler`.

Sources:

- AWS End User Messaging Social (EUM Social) user guide: "Message and event
  format", "Events generated by AWS End User Messaging Social", "WhatsApp
  message status", "Receiving Flow responses and status changes", "Monitoring
  with Amazon EventBridge".
- Meta WhatsApp Cloud API: "Webhooks notification payload reference" and
  "Message templates - components".
- The real code of this template (`ws-handler/index.py`,
  `common/whatsapp/store.py`, `common/whatsapp/messaging.py`).

Legend for "Template today":

- **handled** - stored with its real text and/or applied (status).
- **placeholder** - stored as an inbound message whose text is a placeholder
  such as `[Imagen] <caption>` or `[reaction]`; the payload details are lost.
- **ignored** - parsed but nothing is stored or announced.

Anything marked **to verify on the first deploy** is not stated by the AWS
documentation; capture a real SNS message (CloudWatch logs of ws-handler) before
relying on it.

## 1. The envelope EUM Social publishes to SNS

One event destination per WABA (an SNS topic here, `whatsapp-ws-handler`);
every phone number of the WABA publishes to it. The SNS `Message` is a JSON
string with this shape:

| Field | Type | Meaning | ws-handler |
| --- | --- | --- | --- |
| `context.MetaWabaIds[]` | list of `{wabaId, arn}` | Meta WABA id and the AWS WABA ARN | not read |
| `context.MetaPhoneNumberIds[]` | list of `{metaPhoneNumberId, arn}` | Meta phone number id and the AWS phone number ARN that received the event | `[0].arn` is used as `originationPhoneNumberId` to mark as read and to auto-reply from the same number |
| `whatsAppWebhookEntry` | JSON string (one Meta webhook `entry`) | the Meta payload: `{id, changes: [{field, value}]}` | `parse_entry` decodes it; it also accepts an already-decoded object |
| `aws_account_id` | string | account that owns the WABA | not read |
| `message_timestamp` | ISO 8601 string | when EUM Social published the event | not read |
| `messageId` | UUID string | EUM Social event id (not the WhatsApp `wamid`) | not read |

How ws-handler unwraps it, per SNS record:

| Step | Code |
| --- | --- |
| `Records[].Sns.Message` -> `json.loads` | a non-JSON message is logged and skipped (no retry) |
| `context.MetaPhoneNumberIds[0].arn` | origination phone number for replies |
| `whatsAppWebhookEntry` -> `json.loads` | `parse_entry` |
| `entry.changes[].value.messages[]` | `extract_messages` -> `handle_message` (store, announce, mark as read, auto-reply) |
| `entry.changes[].value.statuses[]` | `extract_statuses` -> `handle_status` (update the stored message, announce) |
| `entry.changes[].field` | **not checked**: any change whose `value` has no `messages`/`statuses` is silently ignored |

Notes:

- The AWS example of a *generated* event (call handover failed) writes the
  context keys in snake case (`meta_waba_ids`, `meta_phone_number_ids`,
  `meta_phone_number_id`, `waba_id`) and `whatsAppWebhookEntry` as an object,
  while the relayed message examples use `MetaPhoneNumberIds` and a JSON
  string. ws-handler only reads the camel-case key, so for such an event the
  origination number is empty. **To verify on the first deploy**: which casing
  real relayed and generated events use.
- SNS delivers at least once. ws-handler skips a message whose `wamid` is
  already stored, and a failure to store makes the invocation fail so Lambda
  retries (then the dead-letter queue).

## 2. Inbound messages (`field: messages`, `value.messages[]`)

Common fields of every message: `from` (sender wa_id, digits), `id` (`wamid.`),
`timestamp` (epoch seconds as a string), `type`. The sender's profile name is in
`value.contacts[] = {wa_id, profile.name}`.

Optional on any message:

- `context` - the message is a reply or a forward: `context.id` is the `wamid`
  it quotes, `context.from` its sender, `context.forwarded` /
  `context.frequently_forwarded` booleans. A quick-reply `button` message also
  carries `context.id` of the template it answers.
- `referral` - the conversation started from a Click-to-WhatsApp ad or a post:
  `source_url`, `source_type` (`ad` / `post`), `source_id`, `headline`, `body`,
  `media_type`, `image_url` / `video_url` / `thumbnail_url`, `ctwa_clid`.
- `errors[]` - present on `unsupported` / `unknown` messages.

Media: every media type carries `<type>.id` (the media id), `<type>.mime_type`
and `<type>.sha256`. Download it with EUM Social `GetWhatsAppMessageMedia`
(`mediaId`, `originationPhoneNumberId`, `destinationS3File`), which writes it
straight to S3. Meta only keeps the media for a limited time, so download it
when the event arrives.

| `type` | Key fields | Media | Template today | Recommended handling |
| --- | --- | --- | --- | --- |
| `text` | `text.body` | no | handled: `body` stored as the message text | keep; read `context.id` to show "reply to", store `referral` on the conversation |
| `image` | `image.id`, `mime_type`, `sha256`, `caption` | yes | placeholder: `[Imagen] <caption>` | download to S3 (section 7), store the key, serve a presigned URL |
| `audio` | `audio.id`, `mime_type`, `voice` (true for a voice note) | yes | placeholder: `[Audio]` | download; transcribe with Amazon Transcribe if an agent must read it |
| `video` | `video.id`, `mime_type`, `sha256`, `caption` | yes | placeholder: `[Video] <caption>` | download; mind the Lambda timeout and the bucket size |
| `document` | `document.id`, `mime_type`, `sha256`, `filename`, `caption` | yes | placeholder: `[Documento] <caption>` | download; keep `filename` as the display name |
| `sticker` | `sticker.id`, `mime_type`, `sha256`, `animated` | yes | placeholder: `[Sticker]` | download (webp) or keep the placeholder |
| `location` | `location.latitude`, `longitude`, `name`, `address`, `url` | no | placeholder: `[Ubicacion]` (coordinates lost) | store the coordinates and render a map link |
| `contacts` | `contacts[]` with `name.formatted_name`, `phones[]`, `emails[]`, `org`, ... | no | placeholder: `[Contacto]` | store the vCard data, show name and phone |
| `interactive` / `button_reply` | `interactive.button_reply.id`, `.title` | no | handled: `title` stored | also store `id`, it is the stable value to branch on |
| `interactive` / `list_reply` | `interactive.list_reply.id`, `.title`, `.description` | no | handled: `title` stored | also store `id` |
| `interactive` / `nfm_reply` (Flows) | `interactive.nfm_reply.response_json` (JSON string), `body`, `name` | no | stored with an **empty** text (no `title`) | parse `response_json` and store the submitted fields |
| `button` (template quick reply) | `button.text`, `button.payload`; `context.id` = template `wamid` | no | handled: `button.text` stored | store `payload`; link to the template sent via `context.id` |
| `reaction` | `reaction.message_id` (wamid reacted to), `reaction.emoji` (empty = removed) | no | placeholder: `[reaction]` stored as a new message, auto-reply fires | do not store as a message; attach the emoji to `message_id` and skip auto-reply |
| `order` | `order.catalog_id`, `order.text`, `order.product_items[]` (`product_retailer_id`, `quantity`, `item_price`, `currency`) | no | placeholder: `[order]` | only relevant with a Meta catalog; store the items |
| `system` | `system.body`, `system.type` (`user_changed_number`, ...), `system.wa_id` / `new_wa_id` | no | placeholder: `[system]` | update the contact's phone; never auto-reply |
| `request_welcome` | no payload; the user opened the chat for the first time | no | placeholder: `[request_welcome]`, auto-reply fires | send a welcome message instead of storing it as a message |
| `unsupported` / `unknown` | `errors[]` (`code`, `title`, `error_data.details`) | no | placeholder: `[unsupported]` / `[unknown]` | store with the error title; do not auto-reply |

Not covered above: `ephemeral`, `edit`, `revoke` and call-related types exist in
recent Meta API versions; they fall into the generic placeholder today.

## 3. Statuses of what we sent (`field: messages`, `value.statuses[]`)

Fields: `id` (the `wamid` we got from `SendWhatsAppMessage`), `status`,
`timestamp`, `recipient_id`, optional `errors[]` and, on billable sends,
`conversation` and `pricing`.

| `status` | Meaning | Template today | Recommended handling |
| --- | --- | --- | --- |
| `sent` | accepted and in transit | handled: `store.update_status` (rank 1) + `MESSAGE_STATUS` event | keep |
| `delivered` | reached the device | handled (rank 2) | keep |
| `read` | read; only when the contact has read receipts on | handled (rank 3) | keep |
| `failed` | not delivered; `errors[]` explains why | handled (rank 4, always wins); `errors[0].title` stored as the reason | also store `errors[0].code` (e.g. 131047 re-engagement, 131026 undeliverable) to drive UI hints |
| `deleted` | the contact deleted the message (listed by AWS) | ignored (not in `STATUS_RANK`) | mark the message as deleted, drop downloaded media |
| `warning` | the message references an unavailable item (listed by AWS) | ignored | log it |
| `accepted` | accepted by WhatsApp for processing (listed by AWS) | ignored | optional |
| `Message retries exhausted, dropping message.` | EUM Social could not hand the message to WhatsApp within 180 minutes (listed by AWS) | ignored | treat as `failed` |
| handover events (`WhatsApp Message Handover Succeeded` / `Failed`) | generated by EUM Social, delivered in the `statuses` field | ignored (not in `STATUS_RANK`) | treat "Failed" as `failed`; **to verify on the first deploy**: the exact `status` string and whether `id` is the `wamid` |

`errors[]` items: `code` (int), `title`, `message`, `error_data.details`, `href`.

`conversation` and `pricing` (not read today):

| Field | Meaning |
| --- | --- |
| `conversation.id` | Meta conversation id |
| `conversation.expiration_timestamp` | when the conversation window closes (epoch seconds) |
| `conversation.origin.type` | `marketing`, `utility`, `authentication`, `service`, ... |
| `pricing.billable` | whether the message is charged |
| `pricing.pricing_model` | `CBP` (per conversation) or `PMP` (per message, newer API versions) |
| `pricing.category` | billing category, same values as `origin.type` |

Recommended: store `pricing.category` / `billable` on the outbound message if
you need cost reports.

## 4. Other WABA webhook fields

These are Meta webhook fields other than `messages`. They arrive in the same
`entry.changes[]`, with `field` set to the name below and a `value` without
`messages` or `statuses`, so **ws-handler ignores all of them today**.

"EUM Social" column:

- **documented** - the AWS guide states it is delivered to the event destination.
- **to verify on the first deploy** - the AWS guide does not mention it. AWS
  says "most events originate as webhook notifications from Meta" and that a
  notification it cannot map is delivered as "WhatsApp Unknown Notification
  Received" with the raw payload, so these may arrive, possibly in that wrapper.
  Do not depend on them until a real event has been seen.

| `field` | Key `value` contents (Meta) | EUM Social | Template today | Recommended handling |
| --- | --- | --- | --- | --- |
| `messages` | `messages[]`, `statuses[]`, `contacts[]`, `metadata` | documented | handled (sections 2 and 3) | - |
| `flows` | `event` (`FLOW_STATUS_CHANGE`, `ENDPOINT_ERROR_RATE`, `ENDPOINT_LATENCY`, `ENDPOINT_AVAILABILITY`, `FLOW_VERSION_EXPIRY_WARNING`), `flow_id`, `old_status`, `new_status` | documented | ignored | alert (log metric) when a Flow is blocked or degraded |
| `calls` | call handover events generated by EUM Social | documented (generated) | ignored | only if you use WhatsApp calling |
| `message_template_status_update` | `event` (APPROVED, REJECTED, PENDING, PAUSED, DISABLED, FLAGGED, REINSTATED, PENDING_DELETION, DELETED, LIMIT_EXCEEDED, IN_APPEAL), `message_template_id`, `message_template_name`, `message_template_language`, `reason` | to verify on the first deploy | ignored | publish an AppSync event so the templates screen refreshes; `GET /whatsapp/templates` already returns the live status |
| `message_template_quality_update` | `previous_quality_score`, `new_quality_score` (GREEN / YELLOW / RED / UNKNOWN), `message_template_id`, `message_template_name`, `message_template_language` | to verify on the first deploy | ignored | surface the quality next to the template; `qualityScore` is also in the templates API |
| `template_category_update` | `message_template_id`, `message_template_name`, `message_template_language`, `previous_category`, `new_category` (or `correct_category`) | to verify on the first deploy | ignored | refresh the template list; a category change changes the price |
| `phone_number_quality_update` | `display_phone_number`, `event` (FLAGGED, UNFLAGGED, ...), `current_limit` (messaging tier) | to verify on the first deploy | ignored | alert operations; a lower tier caps business-initiated conversations |
| `phone_number_name_update` | `display_phone_number`, `decision` (APPROVED / REJECTED / ...), `requested_verified_name`, `rejection_reason` | to verify on the first deploy | ignored | notify the admin |
| `account_update` | `event` (VERIFIED_ACCOUNT, DISABLED_UPDATE, ACCOUNT_VIOLATION, ACCOUNT_RESTRICTION, ...), `ban_info`, `restriction_info`, `violation_info` | to verify on the first deploy | ignored | alert: a restriction can stop all sending |
| `account_review_update` | `decision` (APPROVED / REJECTED / PENDING / DEFERRED) | to verify on the first deploy | ignored | notify the admin |
| `account_alerts` | `entity_type`, `entity_id`, `alert_severity`, `alert_status`, `alert_type`, `alert_description` | to verify on the first deploy | ignored | log and alert |
| `business_capability_update` | `max_daily_conversation_per_phone`, `max_phone_numbers_per_business` (or the newer `max_daily_conversations_per_business`) | to verify on the first deploy | ignored | log |
| `security` | `display_phone_number`, `event` (e.g. PIN_CHANGED, PIN_RESET_REQUEST) | to verify on the first deploy | ignored | alert: two-step PIN changes are security-relevant |
| `user_preferences` | `user_preferences[]` with `wa_id`, `category: "marketing_messages"`, `value` (`stop` / `resume`), `detail`, `timestamp` | to verify on the first deploy | ignored | store a marketing opt-out flag on the conversation and block marketing templates to that contact |

Recommended code change for all of them: branch on `change["field"]` in
ws-handler, keep the current path for `messages`, and log
`field` + a truncated `value` for anything else, so the first deploy shows what
EUM Social really forwards.

## 5. Template variables

Meta allows two formats per template, fixed at creation:

| | Positional | Named |
| --- | --- | --- |
| Placeholder | `{{1}}`, `{{2}}`, ... (sequential) | `{{first_name}}`, `{{order_id}}` (lowercase letters, digits and underscores) |
| `parameter_format` at creation | `POSITIONAL` (default) | `NAMED` |
| Example at creation (body) | `example.body_text: [["Ana", "Monday"]]` | `example.body_text_named_params: [{param_name, example}]` |
| Example at creation (text header) | `example.header_text: ["Ana"]` | `example.header_text_named_params` |
| Send-time parameter | `{"type": "text", "text": "Ana"}` in order | `{"type": "text", "parameter_name": "first_name", "text": "Ana"}` |

Every variable needs a sample value when the template is created, or Meta
rejects it.

Sending maps values per component, in `template.components[]` of the
`SendWhatsAppMessage` payload:

| Component | Send-time shape |
| --- | --- |
| text header with a variable | `{"type": "header", "parameters": [{"type": "text", "text": "..."}]}` |
| media header (IMAGE / VIDEO / DOCUMENT) | `{"type": "header", "parameters": [{"type": "image", "image": {"link": "https://..."}}]}` (or `{"id": "<media id>"}`) |
| location header | `{"type": "header", "parameters": [{"type": "location", "location": {latitude, longitude, name, address}}]}` |
| body | `{"type": "body", "parameters": [...]}`, one per distinct variable |
| URL button with a variable | `{"type": "button", "sub_type": "url", "index": "0", "parameters": [{"type": "text", "text": "<url suffix>"}]}` |
| quick reply button payload | `{"type": "button", "sub_type": "quick_reply", "index": "1", "parameters": [{"type": "payload", "payload": "..."}]}` |
| copy code button | `{"type": "button", "sub_type": "copy_code", "index": "0", "parameters": [{"type": "coupon_code", "coupon_code": "..."}]}` |

Limits (Meta "Message templates - components" page):

| Item | Limit |
| --- | --- |
| Text header | 60 characters, 1 variable |
| Body | 1024 characters, multiple variables |
| Footer | 60 characters, no variables |
| Buttons | up to 10 in total; quick reply label 25 characters |
| URL buttons | up to 2, label 25 characters, URL 2000 characters, 1 variable appended at the end of the URL |
| Phone number button | 1, label 25 characters, number 20 characters |
| Copy code button | 1, example up to 20 characters |

What this template does today:

- `GET /whatsapp/templates` returns every template with `status`,
  `qualityScore`, `header` (text headers only, `null` for media), `body`,
  `footer`, `buttons`, `variables` (distinct body variables), `variableNames`
  and `parameterFormat`.
- `POST /whatsapp/templates/send` only fills **body** variables: it rejects a
  non-APPROVED template (409 `TEMPLATE_NOT_APPROVED`), checks the parameter
  count, and tags each value with `parameter_name` when the template is NAMED.
  Header variables, media headers and button parameters are not sent yet, so a
  template that needs them is rejected by Meta (502).

## 6. How midoc handles media (recommended design)

midoc (`midoc-medical-planner-backend`) already downloads WhatsApp media. Its
flow, in `src/lambda/ws-handler/index.py` and `src/lambda/get-ws-message/index.py`:

| Step | Function | What it does |
| --- | --- | --- |
| 1. Extract | `extract_whatsapp_messages` | for any non-text message keeps `<type>.id` as `media_id`, plus `mime_type` and `filename` |
| 2. Download | `download_media_to_s3` | calls `social_messaging.get_whatsapp_message_media(mediaId, originationPhoneNumberId, metadataOnly=False, destinationS3File={bucketName, key: "media/"})`; EUM Social writes the object straight to S3 and returns `mimeType` and `fileSize` |
| 3. Find the object | `stored_media_key` | EUM Social names the object after the media id and the mime **subtype** (e.g. `.vnd.openxmlformats-...`), so the key is read back with `list_objects_v2(Prefix="media/<media_id>.")`, skipping the Transcribe output `<media_id>.json` |
| 4. Rename | `rename_media` + `MEDIA_EXTENSIONS` | copies to `media/<media_id>.<real extension>` (`jpg`, `pdf`, `docx`, `ogg`, ...; fallback `mimetypes`) with the right `ContentType`, then deletes the original; a failed copy keeps the original key |
| 5. Never lose the message | `store_message_media` | returns `{}` when there is no media or the download fails; the message is stored anyway |
| 6. Store the key | `save_received_message(..., media_id, mime_type, object_key)` | the message item keeps where its media lives |
| 7. Audio | `transcribe_audio_message` -> `transcribe_audio_from_s3` | Amazon Transcribe job over the S3 object (`MediaFormat` from `AUDIO_MEDIA_FORMATS`), output to `media/<media_id>.json`; the text is what the agent reads |
| 8. Serve | `get-ws-message`: `exposed_message` + `media_url` | `media_id` and `object_key` are hidden (`HIDDEN_MEDIA_ATTRIBUTES`); a message with media gets a presigned `get_object` `media_url` (default 3600 s); a URL that cannot be signed leaves that one message without it |

To add media to this template the same way:

1. Add a private media bucket to `WhatsAppFactory` and grant ws-handler
   `social-messaging:GetWhatsAppMessageMedia` plus `s3:PutObject` /
   `GetObject` / `ListBucket` / `DeleteObject` on it (EUM Social writes with
   the caller's permissions; **to verify on the first deploy** whether the
   bucket policy also needs to allow the service).
2. In ws-handler, download in `handle_message` after the duplicate check and
   before `store.save_message`, store `object_key` and `mime_type` on the
   message, keep the placeholder text as the fallback.
3. In `get-messages`, replace `object_key` with a presigned `media_url`.
4. Raise the ws-handler timeout if videos or transcription are expected
   (midoc polls Transcribe synchronously).
