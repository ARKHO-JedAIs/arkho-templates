# WhatsApp events map

What WhatsApp can deliver to this template, what the code does with each event
today, and what we recommend doing with it. For developers extending
`backend/src/lambda/whatsapp/ws-handler`.

Sources:

- AWS End User Messaging Social (EUM Social) user guide: "Message and event
  format", "Events generated by AWS End User Messaging Social", "WhatsApp
  message status", "Receiving Flow responses and status changes", "Monitoring
  with Amazon EventBridge".
- Meta WhatsApp Cloud API: "Webhooks notification payload reference" and
  "Message templates - components".
- The real code of this template (`ws-handler/index.py`,
  `common/whatsapp/store.py`, `common/whatsapp/messaging.py`,
  `common/whatsapp/media.py`).

Legend for "Template today":

- **handled** - stored with a normalized `type`, a readable `message` and a
  `payload` per type (and `media` for files), announced, and drawn by the web.
- **ignored** - parsed but nothing is stored or announced.

Every stored inbound message also keeps, when present, `reply_to`
(`context.id`), `forwarded` (`context.forwarded` / `frequently_forwarded`) and
`referral` (`source_url`, `source_type`, `source_id`, `headline`, `body`,
`media_type`, `ctwa_clid`).

Anything marked **to verify on the first deploy** is not stated by the AWS
documentation; capture a real SNS message (CloudWatch logs of ws-handler) before
relying on it.

## 1. The envelope EUM Social publishes to SNS

One event destination per WABA (an SNS topic here, `whatsapp-ws-handler`);
every phone number of the WABA publishes to it. The SNS `Message` is a JSON
string with this shape:

| Field | Type | Meaning | ws-handler |
| --- | --- | --- | --- |
| `context.MetaWabaIds[]` | list of `{wabaId, arn}` | Meta WABA id and the AWS WABA ARN | not read |
| `context.MetaPhoneNumberIds[]` | list of `{metaPhoneNumberId, arn}` | Meta phone number id and the AWS phone number ARN that received the event | `[0].arn` is used as `originationPhoneNumberId` to mark as read and to auto-reply from the same number |
| `whatsAppWebhookEntry` | JSON string (one Meta webhook `entry`) | the Meta payload: `{id, changes: [{field, value}]}` | `parse_entry` decodes it; it also accepts an already-decoded object |
| `aws_account_id` | string | account that owns the WABA | not read |
| `message_timestamp` | ISO 8601 string | when EUM Social published the event | not read |
| `messageId` | UUID string | EUM Social event id (not the WhatsApp `wamid`) | not read |

How ws-handler unwraps it, per SNS record:

| Step | Code |
| --- | --- |
| `Records[].Sns.Message` -> `json.loads` | a non-JSON message is logged and skipped (no retry) |
| `context.MetaPhoneNumberIds[0].arn` | origination phone number for replies |
| `whatsAppWebhookEntry` -> `json.loads` | `parse_entry` |
| `entry.changes[].value.messages[]` | `extract_messages` (`normalize` per type) -> `handle_message` (download media, store, announce, mark as read, auto-reply) or `handle_reaction` |
| `entry.changes[].value.statuses[]` | `extract_statuses` -> `handle_status` (update the stored message, announce) |
| `entry.changes[].field` | **not checked**: any change whose `value` has no `messages`/`statuses` is silently ignored |

Notes:

- The AWS example of a *generated* event (call handover failed) writes the
  context keys in snake case (`meta_waba_ids`, `meta_phone_number_ids`,
  `meta_phone_number_id`, `waba_id`) and `whatsAppWebhookEntry` as an object,
  while the relayed message examples use `MetaPhoneNumberIds` and a JSON
  string. ws-handler only reads the camel-case key, so for such an event the
  origination number is empty. **To verify on the first deploy**: which casing
  real relayed and generated events use.
- SNS delivers at least once. ws-handler skips a message whose `wamid` is
  already stored, and a failure to store makes the invocation fail so Lambda
  retries (then the dead-letter queue).

## 2. Inbound messages (`field: messages`, `value.messages[]`)

Common fields of every message: `from` (sender wa_id, digits), `id` (`wamid.`),
`timestamp` (epoch seconds as a string), `type`. The sender's profile name is in
`value.contacts[] = {wa_id, profile.name}`.

Optional on any message:

- `context` - the message is a reply or a forward: `context.id` is the `wamid`
  it quotes, `context.from` its sender, `context.forwarded` /
  `context.frequently_forwarded` booleans. A quick-reply `button` message also
  carries `context.id` of the template it answers.
- `referral` - the conversation started from a Click-to-WhatsApp ad or a post:
  `source_url`, `source_type` (`ad` / `post`), `source_id`, `headline`, `body`,
  `media_type`, `image_url` / `video_url` / `thumbnail_url`, `ctwa_clid`.
- `errors[]` - present on `unsupported` / `unknown` messages.

Media: every media type carries `<type>.id` (the media id), `<type>.mime_type`
and `<type>.sha256`. Download it with EUM Social `GetWhatsAppMessageMedia`
(`mediaId`, `originationPhoneNumberId`, `destinationS3File`), which writes it
straight to S3. Meta only keeps the media for a limited time, so download it
when the event arrives (section 6).

Auto-reply: only the types marked "auto-reply" below trigger `answer`
(`AUTO_REPLY_TYPES` in ws-handler). Every stored inbound message except
`system` opens the 24 hour window.

With the AI agent deployed (`AGENT_RUNTIME` agentcore or lambda) and switched
on (`enabled` in the agent-prompt parameter), `answer` queues the same types on
the `agent-jobs` FIFO queue instead of sending the fixed reply:
`{phone, message_id, text, user_name, session_id, actor_id,
origination_phone_number_id}`, where `text` is the stored readable `message`
(media arrives as its placeholder plus caption, e.g. `[Audio]`, until a
transcription is added in `after_media_stored`). `agent-worker` invokes the
agent and sends its reply as an outbound text with `sent_by: agent`; when it
hands the conversation to a person it stores an internal notice with
`payload.kind` `agent_handoff` (third off-topic turn in 24 hours) or
`agent_failed` (the agent could not answer) and publishes `CONTROL_CHANGED`
and `CONVERSATION_EVENT` like a takeover from the web. Over
`AGENT_RATE_LIMIT_PER_HOUR` per customer the agent is not called and one
notice per hour is sent instead (`sent_by: assistant`).

| `type` | Key fields | Media | Template today | Recommended handling |
| --- | --- | --- | --- | --- |
| `text` | `text.body` | no | handled: `type: text`, `message` = body; `reply_to`, `referral` kept; auto-reply | - |
| `image` | `image.id`, `mime_type`, `sha256`, `caption` | yes | handled: downloaded to `media/<id>.jpg`, `media: {key, mimeType, size, caption, sha256}`; the web gets a presigned URL; auto-reply | - |
| `audio` | `audio.id`, `mime_type`, `voice` (true for a voice note) | yes | handled: as image, plus `media.voice`; auto-reply | transcribe in the `after_media_stored` hook (Amazon Transcribe) if an agent must read it |
| `video` | `video.id`, `mime_type`, `sha256`, `caption` | yes | handled: as image (ws-handler timeout 90 s for the download); auto-reply | mind the bucket size: set `MEDIA_RETENTION_DAYS` |
| `document` | `document.id`, `mime_type`, `sha256`, `filename`, `caption` | yes | handled: as image, plus `media.filename` (the display and download name); auto-reply | - |
| `sticker` | `sticker.id`, `mime_type`, `sha256`, `animated` | yes | handled: as image (webp), plus `media.animated`; auto-reply | - |
| `location` | `location.latitude`, `longitude`, `name`, `address`, `url` | no | handled: `payload: {latitude, longitude, name, address, url}` (numbers as DynamoDB Decimals); the web links to Google Maps; auto-reply | - |
| `contacts` | `contacts[]` with `name.formatted_name`, `phones[]`, `emails[]`, `org`, ... | no | handled: `payload.contacts[] = {name, phones[{phone, wa_id, type}], emails[], org}`; auto-reply | - |
| `interactive` / `button_reply` | `interactive.button_reply.id`, `.title` | no | handled: `type: button_reply`, `payload: {id, title}`; auto-reply | branch on `payload.id` in `answer` |
| `interactive` / `list_reply` | `interactive.list_reply.id`, `.title`, `.description` | no | handled: `type: list_reply`, `payload: {id, title, description}`; auto-reply | branch on `payload.id` |
| `interactive` / `nfm_reply` (Flows) | `interactive.nfm_reply.response_json` (JSON string), `body`, `name` | no | handled: `type: nfm_reply`, `payload: {name, body, response}` (`response` parsed; the raw text when it is not JSON); the web shows a key/value card; auto-reply | - |
| `button` (template quick reply) | `button.text`, `button.payload`; `context.id` = template `wamid` | no | handled: `type: button`, `payload: {text, payload}`, `reply_to` = the template `wamid`; auto-reply | - |
| `reaction` | `reaction.message_id` (wamid reacted to), `reaction.emoji` (empty = removed) | no | handled: **not** stored as a message; `reaction: {emoji, date}` set on (or removed from) the target message and announced as `MESSAGE_UPDATED`; no auto-reply, no mark-as-read | - |
| `order` | `order.catalog_id`, `order.text`, `order.product_items[]` (`product_retailer_id`, `quantity`, `item_price`, `currency`) | no | handled: `payload: {catalog_id, text, items[]}`; auto-reply | only relevant with a Meta catalog |
| `system` | `system.body`, `system.type` (`user_changed_number`, ...), `system.wa_id` / `new_wa_id` | no | handled: `payload: {body, type, wa_id, new_wa_id}`; shown as a centered notice; no auto-reply; does not open the window | move the conversation to `new_wa_id` |
| `request_welcome` | no payload; the user opened the chat for the first time | no | handled: stored as a notice; no auto-reply | send a welcome message from `answer`'s caller if you want one |
| `unsupported` / `unknown` / any other type | `errors[]` (`code`, `title`, `error_data.details`) | no | handled: `type: unsupported`, `payload: {original_type, errors[], raw}` (`raw` = the message JSON, 4000 chars); no auto-reply | - |

`ephemeral`, `edit`, `revoke` and call-related types exist in recent Meta API
versions; they are stored as `unsupported` with their raw payload. An
`interactive` message of another subtype is `unsupported` with
`original_type: interactive/<subtype>`.

## 3. Statuses of what we sent (`field: messages`, `value.statuses[]`)

Fields: `id` (the `wamid` we got from `SendWhatsAppMessage`), `status`,
`timestamp`, `recipient_id`, optional `errors[]` and, on billable sends,
`conversation` and `pricing`.

| `status` | Meaning | Template today | Recommended handling |
| --- | --- | --- | --- |
| `sent` | accepted and in transit | handled: `store.update_status` (rank 1) + `MESSAGE_STATUS` event | keep |
| `delivered` | reached the device | handled (rank 2) | keep |
| `read` | read; only when the contact has read receipts on | handled (rank 3) | keep |
| `failed` | not delivered; `errors[]` explains why | handled (rank 4, always wins); `errors[0].title` stored as the reason | also store `errors[0].code` (e.g. 131047 re-engagement, 131026 undeliverable) to drive UI hints |
| `deleted` | the contact deleted the message (listed by AWS) | handled: `deleted: true` on the message (`store.mark_message`) + `MESSAGE_STATUS`; the web shows "Mensaje eliminado" | drop the downloaded media too if your retention rules require it |
| `warning` | the message references an unavailable item (listed by AWS) | handled: logged and stored as `warning` (`errors[0].title`) + `MESSAGE_STATUS` | - |
| `accepted` | accepted by WhatsApp for processing (listed by AWS) | ignored | optional |
| `Message retries exhausted, dropping message.` | EUM Social could not hand the message to WhatsApp within 180 minutes (listed by AWS) | ignored | treat as `failed` |
| handover events (`WhatsApp Message Handover Succeeded` / `Failed`) | generated by EUM Social, delivered in the `statuses` field | ignored (not in `STATUS_RANK`) | treat "Failed" as `failed`; **to verify on the first deploy**: the exact `status` string and whether `id` is the `wamid` |

`errors[]` items: `code` (int), `title`, `message`, `error_data.details`, `href`.

`conversation` and `pricing` (not read today):

| Field | Meaning |
| --- | --- |
| `conversation.id` | Meta conversation id |
| `conversation.expiration_timestamp` | when the conversation window closes (epoch seconds) |
| `conversation.origin.type` | `marketing`, `utility`, `authentication`, `service`, ... |
| `pricing.billable` | whether the message is charged |
| `pricing.pricing_model` | `CBP` (per conversation) or `PMP` (per message, newer API versions) |
| `pricing.category` | billing category, same values as `origin.type` |

Recommended: store `pricing.category` / `billable` on the outbound message if
you need cost reports.

## 4. Other WABA webhook fields

These are Meta webhook fields other than `messages`. They arrive in the same
`entry.changes[]`, with `field` set to the name below and a `value` without
`messages` or `statuses`, so **ws-handler ignores all of them today**.

"EUM Social" column:

- **documented** - the AWS guide states it is delivered to the event destination.
- **to verify on the first deploy** - the AWS guide does not mention it. AWS
  says "most events originate as webhook notifications from Meta" and that a
  notification it cannot map is delivered as "WhatsApp Unknown Notification
  Received" with the raw payload, so these may arrive, possibly in that wrapper.
  Do not depend on them until a real event has been seen.

| `field` | Key `value` contents (Meta) | EUM Social | Template today | Recommended handling |
| --- | --- | --- | --- | --- |
| `messages` | `messages[]`, `statuses[]`, `contacts[]`, `metadata` | documented | handled (sections 2 and 3) | - |
| `flows` | `event` (`FLOW_STATUS_CHANGE`, `ENDPOINT_ERROR_RATE`, `ENDPOINT_LATENCY`, `ENDPOINT_AVAILABILITY`, `FLOW_VERSION_EXPIRY_WARNING`), `flow_id`, `old_status`, `new_status` | documented | ignored | alert (log metric) when a Flow is blocked or degraded |
| `calls` | call handover events generated by EUM Social | documented (generated) | ignored | only if you use WhatsApp calling |
| `message_template_status_update` | `event` (APPROVED, REJECTED, PENDING, PAUSED, DISABLED, FLAGGED, REINSTATED, PENDING_DELETION, DELETED, LIMIT_EXCEEDED, IN_APPEAL), `message_template_id`, `message_template_name`, `message_template_language`, `reason` | to verify on the first deploy | ignored | publish an AppSync event so the templates screen refreshes; `GET /whatsapp/templates` already returns the live status |
| `message_template_quality_update` | `previous_quality_score`, `new_quality_score` (GREEN / YELLOW / RED / UNKNOWN), `message_template_id`, `message_template_name`, `message_template_language` | to verify on the first deploy | ignored | surface the quality next to the template; `qualityScore` is also in the templates API |
| `template_category_update` | `message_template_id`, `message_template_name`, `message_template_language`, `previous_category`, `new_category` (or `correct_category`) | to verify on the first deploy | ignored | refresh the template list; a category change changes the price |
| `phone_number_quality_update` | `display_phone_number`, `event` (FLAGGED, UNFLAGGED, ...), `current_limit` (messaging tier) | to verify on the first deploy | ignored | alert operations; a lower tier caps business-initiated conversations |
| `phone_number_name_update` | `display_phone_number`, `decision` (APPROVED / REJECTED / ...), `requested_verified_name`, `rejection_reason` | to verify on the first deploy | ignored | notify the admin |
| `account_update` | `event` (VERIFIED_ACCOUNT, DISABLED_UPDATE, ACCOUNT_VIOLATION, ACCOUNT_RESTRICTION, ...), `ban_info`, `restriction_info`, `violation_info` | to verify on the first deploy | ignored | alert: a restriction can stop all sending |
| `account_review_update` | `decision` (APPROVED / REJECTED / PENDING / DEFERRED) | to verify on the first deploy | ignored | notify the admin |
| `account_alerts` | `entity_type`, `entity_id`, `alert_severity`, `alert_status`, `alert_type`, `alert_description` | to verify on the first deploy | ignored | log and alert |
| `business_capability_update` | `max_daily_conversation_per_phone`, `max_phone_numbers_per_business` (or the newer `max_daily_conversations_per_business`) | to verify on the first deploy | ignored | log |
| `security` | `display_phone_number`, `event` (e.g. PIN_CHANGED, PIN_RESET_REQUEST) | to verify on the first deploy | ignored | alert: two-step PIN changes are security-relevant |
| `user_preferences` | `user_preferences[]` with `wa_id`, `category: "marketing_messages"`, `value` (`stop` / `resume`), `detail`, `timestamp` | to verify on the first deploy | ignored | store a marketing opt-out flag on the conversation and block marketing templates to that contact |

Recommended code change for all of them: branch on `change["field"]` in
ws-handler, keep the current path for `messages`, and log
`field` + a truncated `value` for anything else, so the first deploy shows what
EUM Social really forwards.

## 5. Template variables

Meta allows two formats per template, fixed at creation:

| | Positional | Named |
| --- | --- | --- |
| Placeholder | `{{1}}`, `{{2}}`, ... (sequential) | `{{first_name}}`, `{{order_id}}` (lowercase letters, digits and underscores) |
| `parameter_format` at creation | `POSITIONAL` (default) | `NAMED` |
| Example at creation (body) | `example.body_text: [["Ana", "Monday"]]` | `example.body_text_named_params: [{param_name, example}]` |
| Example at creation (text header) | `example.header_text: ["Ana"]` | `example.header_text_named_params` |
| Send-time parameter | `{"type": "text", "text": "Ana"}` in order | `{"type": "text", "parameter_name": "first_name", "text": "Ana"}` |

Every variable needs a sample value when the template is created, or Meta
rejects it.

Sending maps values per component, in `template.components[]` of the
`SendWhatsAppMessage` payload:

| Component | Send-time shape |
| --- | --- |
| text header with a variable | `{"type": "header", "parameters": [{"type": "text", "text": "..."}]}` |
| media header (IMAGE / VIDEO / DOCUMENT) | `{"type": "header", "parameters": [{"type": "image", "image": {"link": "https://..."}}]}` (or `{"id": "<media id>"}`) |
| location header | `{"type": "header", "parameters": [{"type": "location", "location": {latitude, longitude, name, address}}]}` |
| body | `{"type": "body", "parameters": [...]}`, one per distinct variable |
| URL button with a variable | `{"type": "button", "sub_type": "url", "index": "0", "parameters": [{"type": "text", "text": "<url suffix>"}]}` |
| quick reply button payload | `{"type": "button", "sub_type": "quick_reply", "index": "1", "parameters": [{"type": "payload", "payload": "..."}]}` |
| copy code button | `{"type": "button", "sub_type": "copy_code", "index": "0", "parameters": [{"type": "coupon_code", "coupon_code": "..."}]}` |

Limits (Meta "Message templates - components" page):

| Item | Limit |
| --- | --- |
| Text header | 60 characters, 1 variable |
| Body | 1024 characters, multiple variables |
| Footer | 60 characters, no variables |
| Buttons | up to 10 in total; quick reply label 25 characters |
| URL buttons | up to 2, label 25 characters, URL 2000 characters, 1 variable appended at the end of the URL |
| Phone number button | 1, label 25 characters, number 20 characters |
| Copy code button | 1, example up to 20 characters |
| Footer, text header | 60 characters (verified on Meta's components page) |

What this template does today:

- `GET /whatsapp/templates` returns every template with `status`,
  `qualityScore`, `header` (text headers only, `null` for media),
  `headerFormat` (`TEXT` / `IMAGE` / `VIDEO` / `DOCUMENT` / `null`),
  `headerVariableNames`, `headerHandle` (the sample of a media header), `body`,
  `footer`, `buttons` (`type`, `text`, plus `url`, `phoneNumber` or the copy
  code `example`), `variables` (distinct body variables), `variableNames`,
  `parameterFormat` and `examples` (the reviewed sample values, keyed
  `header:<variable>`, `body:<variable>`, `button:<index>`).
- `POST /whatsapp/templates/send` fills every part the template needs and
  only those: body variables (`parameters`, in order, tagged with
  `parameter_name` when NAMED), the text header variable (`header.text`,
  tagged too when NAMED), the media header (`header.media`, a file uploaded
  through `upload-url`: checked against the header format, handed to WhatsApp
  with `PostWhatsAppMessageMedia` and sent as `{"type": "image", "image":
  {"id": ...}}`, the document with its `filename`) and the suffix of each URL
  button whose address ends with a variable (`buttons: [{index, text}]`, sent
  as `sub_type: url`). A missing or extra part is 422; a non-APPROVED
  template is 409 `TEMPLATE_NOT_APPROVED`. Quick reply payloads and copy code
  values are not sent (Meta uses the template's own).

### Creating, editing and deleting templates

`templates-admin` (one Lambda behind four routes, so the write permissions
live on one role) serves `POST /whatsapp/templates`,
`PUT /whatsapp/templates/{metaTemplateId}`, `DELETE /whatsapp/templates` and
`POST /whatsapp/templates/media`. `common/whatsapp/templates.py` checks the
request with the web creator's rules (same ids: `name-format`, `body-length`,
`header-media-handle`, `examples-complete`, ...; 422 `TEMPLATE_INVALID`
lists them in `error.details.rules`) and builds Meta's definition:

| Part | Built as |
| --- | --- |
| text header | `{"type": "HEADER", "format": "TEXT", "text", "example": {"header_text": ["..."]}}` (NAMED: `header_text_named_params`) |
| media header | `{"type": "HEADER", "format": "IMAGE", "example": {"header_handle": ["<handle>"]}}` |
| body | `{"type": "BODY", "text", "example": {"body_text": [["...", "..."]]}}` (NAMED: `body_text_named_params: [{param_name, example}]`) |
| footer | `{"type": "FOOTER", "text"}` |
| buttons | `QUICK_REPLY {text}`, `URL {text, url, example: ["<suffix>"]}`, `PHONE_NUMBER {text, phone_number}`, `COPY_CODE {example}` |
| create | `{name, language, category, parameter_format, components}` as `templateDefinition` (up to 6,000 bytes) |
| edit | `templateComponents` (up to 3,000 characters), `parameterFormat` lower case, `templateCategory` only when it changes |
| delete | `templateName` plus `metaTemplateId` (one language); without the id every language of the name |
| header sample | `CreateWhatsAppMessageTemplateMedia(id, sourceS3File)` over an `outbound/` upload -> `metaHeaderHandle` |

Meta's edit rules (developers.facebook.com, "Template management"): only
APPROVED, REJECTED or PAUSED templates can be edited; an approved one up to 10
times in 30 days and once per 24 hours; the category of an approved template
cannot change; the edit replaces every component. Deleting by name deletes
every language; an approved template's name cannot be reused for 30 days.

Verified in the AWS documentation: the request and response of
`CreateWhatsAppMessageTemplate`, `UpdateWhatsAppMessageTemplate`,
`DeleteWhatsAppMessageTemplate` (the boto3 parameter is `deleteAllLanguages`,
query `deleteAllTemplates`; there is no language parameter) and
`CreateWhatsAppMessageTemplateMedia` (returns `metaHeaderHandle`), their
errors, and their IAM resource type (`waba`, no dependent actions, Service
Authorization Reference). **To verify on the first deploy**: whether Meta
accepts `parameter_format` in upper case inside `templateDefinition` (Meta's
components page does not show it; the AWS update call documents lower case);
whether a URL button's `example` is the suffix (Meta's current components page)
or the whole URL (older Meta examples); whether
`CreateWhatsAppMessageTemplateMedia` reads the bucket with the caller's role
(granted `s3:GetObject` on `outbound/*`) or as the service principal (the
bucket policy allows both).

The templates page polls `GET /whatsapp/templates` every 45 seconds while a
template is PENDING (paused while the tab is hidden) and toasts when one is
approved or rejected; wiring `message_template_status_update` (section 4)
would make that push instead of poll.

## 5b. Inbox: unread counters, search and notices

| Feature | Where | What |
| --- | --- | --- |
| Unread counter | `store.touch_conversation(counts_unread=True)` from ws-handler | `ADD unread_count :one` in the same update as the summary (atomic), only for `AUTO_REPLY_TYPES` (customer content: not reactions, `system`, `request_welcome`, `unsupported`, statuses) |
| Reset | `PUT /whatsapp/conversations/{phone}/read` (mark-read) | `SET unread_count = 0` conditioned on the conversation existing; announced as `CONVERSATION_UPDATED` |
| Exposed as | `store.conversation_view` | `unreadCount` (number) in get-conversations and every `CONVERSATION_UPDATED`; `search_key` and `inbox` are hidden |
| Search | `GET /whatsapp/conversations?search=` | `Scan` with `contains(search_key, :term)`, paginated (up to 20 pages, 50 results), sorted by recency; the term is the phone digits when the search is only a number, else the folded text |
| Search key | `touch_conversation` | `"<name lowercase without accents> <phone>"`; a message without a name keeps the existing key (`if_not_exists`) |
| Takeover notice | put-control | when the mode really changes: a message `direction: internal`, `type: event`, `payload: {kind: human_takeover \| assistant_resumed, by}` published as `CONVERSATION_EVENT`; never sent to WhatsApp, never counted as unread, never part of the inbox summary and never opens the window |

Searching inside the messages is out of scope: it needs a search engine
(Amazon OpenSearch Service) fed from the messages table.

## 6. Media

### What this template does

| Step | Where | What |
| --- | --- | --- |
| Bucket | `WhatsAppFactory` | `${projectName}-${envName}-whatsapp-media`: block public access, SSE-S3, SSL only, RETAIN in prod / DESTROY + auto-delete otherwise; optional expiration after `MEDIA_RETENTION_DAYS` (empty = keep forever); incomplete multipart uploads aborted after 1 day; CORS PUT/GET from any origin (presigned URLs carry their own authorization) |
| Download | ws-handler, `media.download_inbound` | `get_whatsapp_message_media(mediaId, originationPhoneNumberId, metadataOnly=False, destinationS3File={bucketName, key: "media/"})`; the object is found with `stored_media_key` (prefix `media/<id>.`) and renamed with `rename_media` / `MEDIA_EXTENSIONS`; the size comes from S3 (the API's `fileSize` is in KB) |
| Never lose the message | ws-handler, `store_media` | a failed download stores the message with `media.error = "download_failed"` |
| Serve | get-messages, ws-handler and send-message announcements, `media.exposed` | `media.key` is replaced by `media.url`, a presigned GET valid for `MEDIA_URL_TTL_SECONDS` (default 900); the key never leaves the backend; the web reloads the conversation when a URL fails |
| Upload | `POST /whatsapp/media/upload-url` (media-upload-url) | `{phone, filename, mimeType, size}` checked against WhatsApp's limits (below); returns a presigned PUT for `outbound/<uuid>.<ext>` signed with that `Content-Type` (5 minutes) |
| Send | `POST /whatsapp/messages` with `{phone, media: {key, mimeType, filename?, caption?}}` | `head_object` checks the upload (key under `outbound/`, same `Content-Type`, size within the limit), `post_whatsapp_message_media(originationPhoneNumberId, sourceS3File)` returns the WhatsApp media id, the message goes out as `image` / `audio` / `video` / `document` (audio without caption, document with `filename`), stored with `media` like an inbound one; the 24 hour window rule still applies |
| Transcription | ws-handler `after_media_stored` | a no-op hook; not included |

Outbound limits (AWS End User Messaging Social "Supported media file types and
sizes in WhatsApp" and Meta Cloud API "Media - Supported media types"):

| Type | MIME types | Max size |
| --- | --- | --- |
| image | `image/jpeg`, `image/png` | 5 MB |
| audio | `audio/aac`, `audio/amr`, `audio/mpeg`, `audio/mp4`, `audio/ogg` (OPUS only, per Meta) | 16 MB |
| video | `video/mp4`, `video/3gpp` (AWS lists `video/3gp`) | 16 MB |
| document | `text/plain`, `application/pdf`, Word, Excel, PowerPoint (`.doc[x]`, `.xls[x]`, `.ppt[x]`) | 100 MB |
| sticker (inbound only) | `image/webp` | 100 KB static, 500 KB animated |

IAM (least privilege, all on `phone-number-id/*` of the account):
ws-handler gets `social-messaging:GetWhatsAppMessageMedia`, `s3:ListBucket`
(prefix `media/`) and `s3:PutObject` / `GetObject` / `DeleteObject` on
`media/*` (plus `GetObject` on `outbound/*` to re-sign sent files);
send-message and send-template (media headers) get
`social-messaging:PostWhatsAppMessageMedia` and `s3:GetObject` on
`outbound/*`; media-upload-url only `s3:PutObject` on `outbound/*`;
get-messages only `s3:GetObject` on both prefixes; templates-admin only
`s3:GetObject` on `outbound/*` plus `CreateWhatsAppMessageTemplate`,
`UpdateWhatsAppMessageTemplate`, `DeleteWhatsAppMessageTemplate` and
`CreateWhatsAppMessageTemplateMedia` on `waba/*` (no other function has them).

Verified in the AWS documentation: the request/response of
`GetWhatsAppMessageMedia` (`fileSize` in KB), that the destination `key` is a
prefix the object name is appended to (the CLI example writes
`inbound_<MEDIA_ID>.jpeg` for `key=inbound_`), that the bucket must be in the
same account and Region as the WABA, the resource type of both actions
(`phone-number-id`, Service Authorization Reference, no dependent actions
listed), and the supported types and sizes. **Not documented, to verify on
the first deploy**: whether EUM Social writes and reads the bucket with the
caller's credentials only or also as the `social-messaging.amazonaws.com`
principal. The bucket policy therefore also allows that principal
`s3:PutObject` / `GetObject` on `media/*` and `outbound/*`, conditioned on
`aws:SourceAccount`; remove the `AllowEndUserMessagingSocialMedia` statement
if the first deploy shows it is not needed. Also to verify: the exact object
name for MIME types with parameters (`audio/ogg; codecs=opus`), which the
prefix lookup tolerates.

Limits worth knowing: API Gateway stops waiting after 29 seconds, so handing a
very large document to WhatsApp from send-message can time out the request
even if the message is sent; the web reloads only the last page of messages
when a URL expires.

### How midoc handles media (the design this follows)

midoc (`midoc-medical-planner-backend`) already downloads WhatsApp media. Its
flow, in `src/lambda/ws-handler/index.py` and `src/lambda/get-ws-message/index.py`:

| Step | Function | What it does |
| --- | --- | --- |
| 1. Extract | `extract_whatsapp_messages` | for any non-text message keeps `<type>.id` as `media_id`, plus `mime_type` and `filename` |
| 2. Download | `download_media_to_s3` | calls `social_messaging.get_whatsapp_message_media(mediaId, originationPhoneNumberId, metadataOnly=False, destinationS3File={bucketName, key: "media/"})`; EUM Social writes the object straight to S3 and returns `mimeType` and `fileSize` |
| 3. Find the object | `stored_media_key` | EUM Social names the object after the media id and the mime **subtype** (e.g. `.vnd.openxmlformats-...`), so the key is read back with `list_objects_v2(Prefix="media/<media_id>.")`, skipping the Transcribe output `<media_id>.json` |
| 4. Rename | `rename_media` + `MEDIA_EXTENSIONS` | copies to `media/<media_id>.<real extension>` (`jpg`, `pdf`, `docx`, `ogg`, ...; fallback `mimetypes`) with the right `ContentType`, then deletes the original; a failed copy keeps the original key |
| 5. Never lose the message | `store_message_media` | returns `{}` when there is no media or the download fails; the message is stored anyway |
| 6. Store the key | `save_received_message(..., media_id, mime_type, object_key)` | the message item keeps where its media lives |
| 7. Audio | `transcribe_audio_message` -> `transcribe_audio_from_s3` | Amazon Transcribe job over the S3 object (`MediaFormat` from `AUDIO_MEDIA_FORMATS`), output to `media/<media_id>.json`; the text is what the agent reads |
| 8. Serve | `get-ws-message`: `exposed_message` + `media_url` | `media_id` and `object_key` are hidden (`HIDDEN_MEDIA_ATTRIBUTES`); a message with media gets a presigned `get_object` `media_url` (default 3600 s); a URL that cannot be signed leaves that one message without it |

Differences from midoc: the presigned URL lasts 15 minutes instead of an
hour and the web refreshes it, the key is never returned (also not in the
AppSync events), a failed download is stored as `media.error` instead of an
empty media, outbound files are supported, and transcription is left as a hook.
